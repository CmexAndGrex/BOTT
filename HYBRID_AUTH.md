# Гибридная авторизация бойцов (Этап 1)

Система входа для бойцов ATK RED: основной быстрый вход через Discord OAuth2 и
резервный — по позывному и паролю. Плюс анкета новобранца, личный кабинет и
панель модерации с записью бойца в Google Таблицу ШДС.

## Как это устроено

Панель работает на собственной JWT-схеме (`jose` + httpOnly-cookie), а не на
NextAuth:

| Что | Cookie | Срок | Отзыв |
|-----|--------|------|-------|
| Сессия панели (`users`) | `auth_token` | 12 часов | `token_version` |
| Сессия бойца (`division_members`) | `member_token` | 7 суток | `member_token_version` |

Обе cookie подписаны одним `JWT_SECRET` и отличаются полем `purpose` в токене
(`panel_session` / `member_session`), поэтому подстановка одной вместо другой
невозможна. Сессия администратора и сессия бойца могут существовать
одновременно: командир входит в панель и отдельно — в свой кабинет.

### Вход администраторов и командиров через Discord

У учётной записи панели (`users`) есть колонка `discord_id` (nullable, unique).
Если вошедший через Discord человек привязан к такой записи с ролью
`admin`/`officer`, callback сразу выдаёт ему **сессию панели** (`auth_token`) и
уводит на `/`, — логин и пароль вводить не нужно. Если он ещё и боец в строю,
рядом ставится cookie кабинета: обе сессии живут одновременно.

Привязка выполняется в панели: **Доступы** (`/users`, только администратор) →
колонка «Discord ID» или селект «Связка с бойцом». Связка с бойцом поднимает
его уровень доступа до роли аккаунта (никогда не понижает) и переносит его
Discord ID на аккаунт. Вход по логину и паролю сохраняется как резервный
способ — на случай недоступности Discord. Роль из Discord никогда не
«повышается»: нештатная роль в учётной записи доступа к панели не даёт.

**Отдельной переменной `NEXTAUTH_URL` нет и не требуется.** Адрес возврата
OAuth2 вычисляется из фактического адреса запроса (учитываются
`X-Forwarded-Proto`/`X-Forwarded-Host`), при необходимости задаётся
`DISCORD_REDIRECT_URI`.

### Связка учётной записи панели с бойцом

Вход в панель открывает **и личный кабинет**, если учётная запись связана с
бойцом. Связка хранится в `users.member_id` (уникальна, `ON DELETE SET NULL`) и
заполняется тремя путями: Dev-Login, раздел **Доступы** → «Связка с бойцом»
(`linkMemberId`), и `scripts/bootstrap-admin.ts`. Если колонка пуста, боец
определяется по подтверждённому `discord_id` (приоритет) или по позывному —
правило живёт в `src/lib/panel-link.ts` и покрыто тестами.

Зачем: раньше связка возникала только при входе через Discord, поэтому командир,
вошедший по логину и паролю, открывал `/profile` и видел заглушку «Войдите в
личный кабинет». Кнопка «Войти» вела на `/login`, после входа человек снова
попадал на ту же заглушку — цикл. Теперь:

- вход в панель (`/api/auth`), Dev-Login и OAuth2 выпускают cookie кабинета
  связанному бойцу (`attachCabinetSession`), а `getSessionMember` умеет
  разрешать бойца и по сессии панели;
- состояния кабинета различимы: `no_session` (401, «войдите») против
  `not_linked` (409, «свяжите аккаунт с бойцом в Доступах») — второй больше не
  предлагает войти повторно, потому что человек уже вошёл;
- отказ middleware ведёт на `/login?next=<путь>`, и после входа страница входа
  возвращает туда же (`safeRedirectPath` отсекает чужие домены — иначе это был
  бы открытый редирект).

Пункт меню: **Личный кабинет** (`/profile`, иконка `IdCard`) — виден любой
действующей сессии, подсвечивается активным на странице кабинета.

### Путь новобранца

1. `/apply` — анкета: позывной, пароль, возраст, опыт в Arma 3, специализация,
   комментарий. Создаётся запись со статусом `pending`.
2. Кандидат может сначала нажать «Войти через Discord»: тогда callback сохраняет
   Discord ID, ник и аватар в httpOnly-cookie, и форма подставит их сама.
3. `/admin/recruits` — штаб проверяет анкету, правит позывной, при
   необходимости вписывает Discord ID, назначает звание и подразделение.
4. **Одобрить** — статус `active`, и боец дописывается в Google Таблицу ШДС
   через существующий `src/lib/gsheets.ts` (сценарий «Добавление в ШДС»).
   **Отклонить** — статус `dismissed`, вход закрывается, выданные сессии
   отзываются.

### Доступ по статусам

| Статус | Вход | Личный кабинет |
|--------|------|----------------|
| `pending` | закрыт, показывается «рапорт на рассмотрении штаба» | нет |
| `active` | есть | есть (В строю) |
| `vacation` | есть | есть (Отпуск) |
| `dismissed` | закрыт | нет |

## Подразделения и Google Таблица

Значения подразделений — это **названия листов** таблицы, их переименование
сломает синхронизацию:

- `Танковая рота` — лист с колонкой C;
- `Артиллерийский дивизион` — лист с колонкой D.

Значения заданы в `UNITS` (`src/lib/recruits.ts`); модерация выбирает их из
списка, произвольный текст отклоняется сервером. Звания — в `RANKS` (совпадают
с ролями Discord из `src/lib/roles.ts`).

## Переменные окружения

```env
# Основной вход через Discord (без них кнопка Discord отключается,
# вход по позывному и паролю продолжает работать)
DISCORD_CLIENT_ID=
DISCORD_CLIENT_SECRET=

# Необязательно: адрес возврата, если он отличается от адреса приложения
# DISCORD_REDIRECT_URI=https://panel.домен/api/auth/discord/callback
```

Адрес из `OAuth2 → Redirects` в Discord Developer Portal должен совпадать с
фактическим: `http://localhost:3001/api/auth/discord/callback` для разработки,
`https://<домен>/api/auth/discord/callback` для прода.

Принимаются и исторические опечатки `DISCROD_CLIENT_ID` / `DISCROD_CLIENT_SECRET`.

## Приватность полей состава

Колонка **Discord ID** — рабочий инструмент штаба, а не публичные данные: по
этому идентификатору человека можно упомянуть и увести в личку. Поэтому:

- в табеле («Состав») и в обзоре («Должники по онлайну») колонка Discord ID и
  служебные статусы («нет ID») видны только роли `admin`/`officer` — как у
  сессии панели, так и у командира, вошедшего в кабинет;
- `GET /api/members` обнуляет `discordId` всем остальным: то, что уехало в
  браузер, спрятать уже нельзя, поэтому проверка стоит на сервере, а не в
  разметке;
- остальным бойцам табель показывается по-военному: **Позывной · Звание и
  должность · Онлайн · Статус** (в строю / в отпуске / выбыл).

Правило описано в `canViewPrivateFields()` (`src/lib/validation.ts`) — один и
тот же код используют роут и интерфейс.

## База данных

К `division_members` добавлены: `callsign` (unique), `password_hash`, `rank`,
`unit`, `status`, `role`, `avatar_url`, `application_data` (jsonb),
`member_token_version`, `created_at`. Новая таблица `member_sessions` — журнал
входов (кто, каким способом, с какого IP). К `users` добавлены колонки
`discord_id` (varchar(32), nullable, unique) — связка с Discord, и
`member_id` (integer, nullable, unique, `ON DELETE SET NULL`) — связка с бойцом,
по которой сессия панели открывает личный кабинет.

Схема применяется автоматически: Docker-сервис `migrate` вызывает
`drizzle-kit push`. Для уже работающей базы, обновляемой вручную, есть
инкрементальные миграции:

```bash
psql "$DATABASE_URL" -f scripts/migrations/2026-09-hybrid-auth.sql
psql "$DATABASE_URL" -f scripts/migrations/2026-09-panel-discord-link.sql
psql "$DATABASE_URL" -f scripts/migrations/2026-09-panel-member-link.sql
```

Последняя миграция не только добавляет колонку, но и заполняет связку для уже
существующих аккаунтов: сперва по совпадению `discord_id`, затем по позывному.

Миграция идемпотентна (повторный запуск ничего не ломает) и переводит бойцов,
уже находящихся в строю, из `pending` в `active`.

## Что важно для эксплуатации

- **Пароль обязателен при подаче рапорта.** Если у бойца нет ни пароля, ни
  Discord, одобрение отклоняется: иначе в кабинет нельзя будет войти.
- **Подразделение обязательно при одобрении** — от него зависит лист таблицы.
- **Одобрение пишет в таблицу, но не отменяется при её сбое.** Если таблица
  недоступна, боец всё равно зачисляется (решение штаба не теряется), а ошибка
  синхронизации показывается модератору и попадает в журнал — повторите
  одобрение или поправьте настройки Google.
- **Возврат из отпуска таблицу не трогает**: боец в ней уже есть, повторная
  запись заняла бы новую строку «Вакант».
- **Смена пароля отзывает остальные сессии** (включая выданные через Discord) и
  перевыпускает cookie текущему браузеру.
- **Отвязка Discord разрешена только при наличии пароля** — чтобы боец не
  остался без способа входа.
- Бойцы, появившиеся в составе через синхронизацию с rs-red.com, имеют статус
  `pending` и не имеют пароля, поэтому в очередь рапортов они не попадают
  (видны во вкладке «Все»).

## Проверка

```bash
npm run typecheck   # строгая типизация
npm run test        # тесты, включая tests/recruits.test.ts
npm run lint        # бюджет замечаний ESLint
npm run build       # production-сборка
```

Сценарий кабинета целиком проверяется двумя скриптами (им нужен запущенный
стенд и заполненная база — `npm run dev:seed`):

```bash
# Серверная часть: редиректы, cookie, коды ответов
node --import ./tests/setup.mjs scripts/verify-profile-flow.mjs http://localhost:3000

# Клиентская часть: пункт меню, подсветка, отрисовка досье (headless Chrome)
node scripts/verify-profile-browser.mjs http://localhost:3000
```

Браузерная проверка управляет Chrome/Edge напрямую по протоколу DevTools, без
дополнительных зависимостей. Если браузера нет в стандартных путях, укажите свой
в `CANDIDATES` внутри скрипта.
