# RED OPS · регламент сквозного тестирования на тестовом Discord-сервере

Документ описывает **полный прогон** бота и панели на тестовом (staging) Discord-сервере
перед боевым релизом: как поднять полигон, как проверить каждый сценарий по цепочке
«действие в интерфейсе → запись в PostgreSQL → ячейка Google Таблицы ШДС → роль в Discord»,
как читать логи и как откатить тестовые данные.

Все названия файлов, настроек, таблиц и ячеек в документе взяты из фактического кода проекта
(ссылки на файлы даны в тексте), а не из предположений. Где код ведёт себя не так, как ожидается
«на словах», это отмечено отдельно — это тоже часть регламента.

# ЧАСТЬ 1. ПОДГОТОВКА ТЕСТОВОГО ОКРУЖЕНИЯ

## 1.1. Тестовый Discord-сервер и полигон

1. Создайте **отдельный** сервер «АТК · STAGING». Боевой сервер не подходит: бот реально
   меняет роли живым людям.
2. Создайте каналы (можно совместить, но лучше разделить — как в бою):

   | Назначение | Настройка |
   |---|---|
   | `#шдс-тест` — заявки ШДС | `shds_channel_id` |
   | `#отпуск-тест` — заявки на отпуск | `vacation_channel_id` |
   | `#роли-тест` — запросы ролей | `roles_channel_id` |
   | `#рапорты-тест` — рапорты состава | `reports_channel_id` (пусто → публикация в канал ШДС, см. `reportsChannelId()` в `src/lib/review.ts`) |
   | `#пинги-тест` — пинги и отчёты | `discord_channel_id` |
   | `#проверки-тест` — контроль вышедших | `left_check_channel_id` (пусто → берётся `discord_channel_id`) |

3. Скопируйте Google Таблицу ШДС: **Файл → Создать копию**. Тестируйте на копии, её ID
   вставьте в настройку `gsheet_spreadsheet_id`. Боевой документ трогать нельзя.

## 1.2. Роли, которыми управляет бот

Полный перечень из кода (`src/lib/roles.ts`, `src/lib/settings.ts`):

| Группа | Роли | Как задаётся ID |
|---|---|---|
| **Звания** (14 ролей Discord) | Рядовой, Ефрейтор, Мл. Сержант, Сержант, Ст. Сержант, Старшина, Прапорщик, Ст. Прапорщик, Лейтенант, Ст. Лейтенант, Капитан, Майор, Подполковник, Полковник | **зашиты в код** — `RANK_ROLE_IDS` |
| **Подразделения** | Танковая рота (суффикс «ТР»), Артиллерийский дивизион (суффикс «АД») | **зашиты в код** — `SUBDIV_ROLE_IDS` |
| **Общие роли клана** | Новобранец, Друг АТК, Артиллерийско-Танковый Корпус, категория «Звания» | **зашиты в код** — `COMMON_ROLE_IDS` |
| **«Берет»** | Берет | `beret_role_id`; если пусто — поиск роли **по имени «Берет»** (`resolveBeretRoleId`) |
| **«Отпуск»** | Отпуск | `leave_role_id` — обязательна для бота |
| **«Запас»** | роль запаса | `reserve_role_id` |
| **Модератор заявок** | роль-модератор | `moderator_role_id` — обязательна |
| **Командирский состав** | пинг при контроле вышедших; только она одобряет «Убрать из таблицы» | `command_role_id` — обязательна |
| **Должности** | любые роли из списка «должность = ID роли» | `post_role_map`, по строке на пару: `Механик-водитель = 1090320507288699020` |
| **Роль для пинга на операцию** | кого упоминать в пинге | `discord_role_id` |

> ℹ️ **Тонкость про звания.** В панели список званий (`RANKS`) начинается с **«Курсант»**, но роли
> `Курсант` на сервере **нет** — в `RANK_ROLE_IDS` её не существует. То есть боец со званием
> «Курсант» (в том числе только что зачисленный — это `DEFAULT_RANK`) при сверке не получит
> никакой роли звания, и это правильное поведение, а не пропуск. Для проверки выдачи звания
> ставьте бойцу «Рядовой» и выше.

Роли, которые бот **не трогает никогда** (`computeRoleDelta` в `src/lib/role-sync.ts`):

- `@everyone`;
- роли ботов и интеграций (Discord помечает их `managed`);
- любые роли **вне справочника** — кастомные «Игроман», «Модератор», «Член профсоюза»;
- защищённый список из настроек: `moderator_role_id`, `command_role_id`, `reserve_role_id` —
  их ведёт штаб руками.

Пятая защита — важная для тестов: **у бойца с неполной карточкой сверка только выдаёт роли,
но ничего не снимает.** Если у бойца не заполнено подразделение, «снятия отложены до заполнения
данных» — иначе боец потерял бы звание на первом же цикле. В отчёте это видно как
`карточка неполная: снятие N рол(и) отложено до заполнения данных`.

Полный комплект ролей бойца, который выдаёт сверка, — это звание + подразделение + общие роли
(Артиллерийско-Танковый Корпус, категория «Звания»), а для остальных состояний — «Отпуск»,
«Запас» и роль должности из `post_role_map`.

> ⚠️ **Критично для стенда.** ID званий, подразделений и общих ролей клана **зашиты в код** и
> указывают на боевой сервер. На тестовом сервере они либо не существуют, либо принадлежат
> другим ролям. Поэтому:
> - полноценно на стенде проверяются роли **из настроек**: `Отпуск`, `Запас`, `Берет`,
>   должности, защищённые;
> - чтобы прогнать полный комплект («звание + подразделение + корпус + категория»), временно
>   подмените константы в `src/lib/roles.ts` (`PRIVATE_ROLE_ID`, `RANK_ROLE_IDS`,
>   `SUBDIV_ROLE_IDS`, `COMMON_ROLE_IDS`) на ID ролей **тестового** сервера;
> - перед релизом обязательно верните их: `git diff src/lib/roles.ts` должен быть пустым.

## 1.3. Иерархия ролей: роль бота должна быть выше всех

Discord запрещает участнику выдавать или снимать роль, стоящую **выше его собственной** в списке
ролей сервера. Если роль бота стоит ниже:

- Discord API вернёт `Missing Permissions`;
- сверка ролей **не упадёт целиком** — бойцы обрабатываются по одному, ошибки копятся в отчёте;
- в журнале появится ошибка по конкретному бойцу, а внешне это выглядит как «звание не сменилось».

Порядок в «Настройки сервера → Роли»:

```
1. Владелец / Администратор
2. ATK RED OPS          <- роль БОТА: выше всех управляемых
3. Полковник ... Рядовой (14 званий)
4. Танковая рота / Артиллерийский дивизион
5. Артиллерийско-Танковый Корпус, категория «Звания»
6. Командирский состав / Модератор / Запас
7. Отпуск, Берет, роли должностей
последняя: @everyone
```

Проверка: у роли бота включено право «Управление ролями», а её позиция выше **любой** роли из
таблицы 1.2.

## 1.4. Права бота и ссылка-приглашение

1. **Discord Developer Portal → приложение → Bot:**
   - Privileged Gateway Intents: включить `SERVER MEMBERS` и `MESSAGE CONTENT`
     (код запрашивает `GuildMembers` и `MessageContent` в конструкторе `Client` в `src/lib/bot.ts`);
   - Bot → Reset Token → скопировать токен.
2. **Права (Permissions)**, которые реально нужны по коду:

   | Право | Зачем |
   |---|---|
   | Manage Roles | выдача и снятие ролей (`addGuildMemberRole` / `removeGuildMemberRole` в `src/lib/discord.ts`) |
   | View Channels | чтение каналов заявок и запросов ролей |
   | Send Messages | пинги на операцию, сообщения в каналах |
   | Send Messages in Threads | ответы в ветке-итоге заявки |
   | Create Public Threads | ветка-итог под заявкой (`startThread` в `ensureThread`) |
   | Embed Links | Embed-сообщения заявок, рапортов и отчётов |
   | Read Message History | чтение текста заявки, на которую поставили реакцию |
   | Add Reactions | бот сам ставит ✅ ❌ ⏰ ❓ в пинге на операцию |

3. **Ссылка-приглашение** (`CLIENT_ID` — ID приложения):

   ```
   https://discord.com/api/oauth2/authorize?client_id=CLIENT_ID&permissions=326686067776&scope=bot%20applications.commands
   ```

   `326686067776` — сумма прав из таблицы выше. На тестовом сервере допустимо выдать боту
   «Администратор» (быстрее), на боевом — только перечисленный набор.

4. Роль для пинга (`discord_role_id`) должна быть разрешена к упоминанию
   (Настройки сервера → Роли → «Разрешить упоминание этой роли»). Право «Mention All Roles»
   боту не нужно.

### 1.5.2. ID сервера — ключ `guild_id`

Ключ `guild_id` читается при выдаче ролей (`resolveGuildId` в `src/lib/review.ts`) и в сверке
(`src/lib/role-sync.ts`). Если он **не задан**, а бот состоит более чем на одном сервере, выдача
ролей и сверка отказываются работать. При единственном сервере у бота он определяется сам.

Поля в интерфейсе настроек для `guild_id` **нет** — задайте значение одним из способов.

**Способ А — SQL (работает всегда):**

```powershell
docker compose exec db psql -U postgres -d app_db -c "INSERT INTO bot_settings (key, value) VALUES ('guild_id', 'ID_ТЕСТОВОГО_СЕРВЕРА') ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value;"
```

**Способ Б — API** (нужна cookie администратора):

```powershell
curl -X PUT http://localhost:3000/api/settings -H "Content-Type: application/json" --cookie "auth_token=ВАША_COOKIE" -d '{\"guild_id\":\"ID_ТЕСТОВОГО_СЕРВЕРА\"}'
```

Кэш настроек — 5 секунд (`getSettings` в `src/lib/settings.ts`), перезапуск контейнера не нужен.

бросает ошибку, и бот пишет в консоль `Не заданы обязательные настройки бота: …`.
Заявки в этом состоянии не обрабатываются — это ожидаемое поведение, а не «поломка».

Где взять ID: Настройки пользователя → **Расширенные** → включить **Режим разработчика**,
далее ПКМ по роли или каналу → «Копировать ID».

### 1.5.4. Блок «Контроль ролей исключённых» (Настройки → задача №5)

Появился в предрелизном аудите. Карточка **«Контроль ролей исключённых»** (eyebrow
«задача №5 · исключённые бойцы») содержит три элемента; значения по умолчанию —
`DEFAULT_SETTINGS` в [`src/lib/settings.ts`](src/lib/settings.ts:100):

| Элемент интерфейса | Ключ в БД | Значение по умолчанию | Границы |
|---|---|---|---|
| тумблер **«вкл»** | `roles_monitor_enabled` | `true` | — |
| поле **«ID канала уведомлений»** | `roles_monitor_channel_id` | пусто | пусто → `left_check_channel_id` → `discord_channel_id` |
| поле **«Срок ожидания, часов»** | `roles_monitor_delay_hours` | `24` | 1…720 (константы `ROLES_ALERT_MIN_HOURS` / `ROLES_ALERT_MAX_HOURS`) |

Планировщик запускает задачу **раз в 30 минут** (`claim('roles-monitor:<получасовой слот>')`
в [`src/lib/scheduler.ts`](src/lib/scheduler.ts:125)) — и только если тумблер включён.

> ⚠️ **Пустой канал — это ошибка конфигурации, а не «тишина».** Если не задан ни один из трёх
> каналов, задача завершается с `ok: false` и текстом «Не задан канал уведомлений: укажите
> roles_monitor_channel_id, left_check_channel_id или discord_channel_id», и эта запись видна
> в журнале под `kind = 'roles-monitor'`. Так же ведёт себя пустой `guild_id` при боте на
> нескольких серверах: «Не задан guild_id и бот состоит на нескольких серверах».

### 1.5.5. Переключение режима сверки ролей: симуляция → боевой

Сверка консервативна по умолчанию (`DEFAULT_SETTINGS` в `src/lib/settings.ts`):

- `role_sync_enabled` — тумблер **«вкл» / Фоновая сверка ролей**, изначально `false`;
- `role_sync_dry_run` — тумблер **«проверка» / «Роли не менять»**, изначально `true`;
- `role_sync_interval_min` — интервал фоновой сверки, по умолчанию `30` минут (допустимо 5…1440).

Порядок вывода в бой:

1. Панель → **Настройки**: сверка **выключена**, «Роли не менять» **включено**.
2. **Обслуживание системы** → карточка «Сверка ролей Discord» → **«Проверить без изменений»**
   (роут `POST /api/admin/maintenance/roles?mode=dry`). Расхождения считаются и пишутся в журнал,
   роли **не меняются**.
3. Разобрать отчёт: **Журнал** → «Редактирование» → запись о сверке; в деталях — счётчики
   («Выдано ролей», «Снято ролей») и список изменений.
4. Отчёт корректен → включить тумблер **вкл**, затем **снять** тумблер «Роли не менять».
   Только теперь сверка реально меняет роли, в том числе фоновая (раз в 30 минут).

> ⚠️ **Особенность кода.** Кнопка **«Применить сейчас»** (`mode=apply`) выполняет изменения
> **независимо** от тумблера «Роли не менять»: явно переданный `dryRun` имеет приоритет внутри
> `syncGuildRoles` (`src/lib/role-sync-runtime.ts`). На стенде это удобно — у роута есть параметр
> `member`, позволяющий сверить одного бойца:
>
> ```
> POST /api/admin/maintenance/roles?mode=apply&member=42
> ```
>
> На боевом сервере нажимать «Применить сейчас» нужно осознанно: без `member` сверка пройдёт по
> всему составу.

## Сценарий 1. Заявка на вступление → зачисление → запись в ШДС

Здесь важно не перепутать **два разных пути** зачисления — в проекте их два:

| Путь | Где в интерфейсе | Что делает |
|---|---|---|
| **A. Одобрение заявки** | `/admin/reports` → вкладка **«Заявки на вступление»** → «Одобрить» | создаёт бойца из `recruit_applications` (`approveRecruitApplication` в `src/lib/review.ts`), выдаёт временный пароль, отправляет ЛС и роль **«Новобранец»**. **Подразделение не назначается** (`unit = null`) |
| **B. Правка карточки в табеле** | `/admin/recruits` → карточка бойца → «Сохранить» / «Зачислить» | `PATCH /api/admin/recruits/[id]`: правит существующего бойца, назначает звание, подразделение и уровень доступа. **Только здесь боец попадёт в ШДС** |

Это разделение намеренное: подразделение определяет лист таблицы, поэтому его ставит штаб руками,
а не заявка.

**Шаг 1.1 — привязка Discord ID**

| Звено | Что происходит |
|---|---|
| Интерфейс | `/members` → колонка **Discord ID** у бойца → нажать на кнопку-ячейку → в модальном окне ввести ID тестового аккаунта → **«Сохранить»** (Enter) |
| Postgres | `SELECT id, callsign, discord_id FROM division_members WHERE callsign = '<позывной>';` |
| ШДС | записана ячейка Discord ID: **три столбца правее колонки имени** — у роты `C` → **`F`**, у дивизиона `D` → **`G`** (см. `syncDiscordIdToSheet` в `src/lib/gsheets.ts`) |
| Discord | изменений нет |

Роут: `PATCH /api/admin/roster/[id]/discord-id` — **только администратор**. Порядок в нём
намеренный: сначала запись в PostgreSQL, потом ячейка в таблице. Если Google недоступен, правка в
базе **не откатывается**, а панель показывает предупреждение
`ID сохранён в панели, но Google Таблица не обновлена: …` — это ожидаемое поведение, а не сбой.

Проверьте два отказа:

- ввод `123` → `Discord ID — от 17 до 19 цифр (введено 3)`;
- у бойца **не назначено подразделение** → в ответе `sheets.ok = false` с текстом
  `«У бойца не назначено подразделение — лист ШДС не определён»`; в базе ID всё равно сохранится.

Снятие привязки — штатное действие: пустое поле (кнопка в модальном окне) очищает и базу, и ячейку.

**Шаг 1.2 — одобрение заявки на вступление (путь A)**

| Звено | Что происходит |
|---|---|
| Интерфейс | боец отправляет заявку через форму; модератор → `/admin/reports` → вкладка **«Заявки на вступление»** → **«Одобрить»** |
| Postgres | создан боец: `unit = NULL`, `status = 'active'`, `role = 'recruit'`, звание **«Курсант»** (`DEFAULT_RANK`), есть `password_hash`; в `recruit_applications` — `status = 'approved'`, `member_id`, `reviewed_by` |
| ШДС | **изменений нет** — подразделение не назначено, лист неизвестен |
| Discord | выдана роль **«Новобранец»** (`COMMON_ROLE_IDS.RECRUIT`), бойцу ушло ЛС с временным паролем |

Проверки-отказы (обязательно прогнать все три):

| Ситуация | Ожидание |
|---|---|
| позывной заявки уже занят бойцом | `Позывной «…» уже занят — поправьте его в панели модерации` |
| у заявки пустой позывной | «У заявки нет позывного» |
| заявка уже одобрена/отклонена | «Решение уже принято» |
| ЛС рекрута закрыты | зачисление **всё равно состоялось**, а офицеру показан временный пароль для передачи вручную |

**Шаг 1.3 — попытка зачислить в табель без подразделения (путь B)**

| Звено | Что происходит |
|---|---|
| Интерфейс | `/admin/recruits` → карточка бойца → поле «Подразделение» пустое → **«Зачислить»** |
| Ожидание | красная плашка `Выберите подразделение — от него зависит лист Google Таблицы` |
| Postgres | `SELECT status, unit, active FROM division_members WHERE id = <id>;` — **ничего не изменилось** |

**Шаг 1.4 — зачисление с подразделением (путь B)**

| Звено | Что происходит |
|---|---|
| Интерфейс | то же окно: «Подразделение» = **Танковая рота**, звание = **Рядовой**, затем **«Зачислить»** |
| Postgres | `status = 'active'`, `active = true`, `unit = 'Танковая рота'`, `role = 'member'`; в `application_data` — `reviewedBy` и `reviewedAt` |
| ШДС | боец дописан в свободную строку **«Вакант»** листа роты (`applyShdsRequest`, действие «Добавление в ШДС», диапазон 42–56): `B` — звание («Рядовой», «Курсант» в лист не пишется), `C` — имя (залито зелёным), `D` — должность («Логист-снабженец/резерв», если боец её не указал), `E` — Steam ID, `F` — Discord ID. На строку скопирован формат соседней строки секции и наложены сплошные тонкие границы от B до W |
| Discord | изменений нет: зачисление роли не выдаёт. Из данных заявки роли выдаёт **бот** при обработке заявки в канале ШДС и **сверка** (сценарий 2) |

Проверка таблицы: `npm run verify:sheet` (скрипт только читает: покажет состав по листам,
свободные строки «Вакант», лист «Запас» и бойцов без Discord ID).

Если таблица не обновилась, панель покажет `Боец зачислен, но запись в Google Таблицу не удалась: …`
— зачисление при этом остаётся в силе (решение штаба не теряется).

**Откат:** `UPDATE division_members SET status = 'pending', active = false, unit = NULL WHERE id = <id>;`,
удалить добавленную строку из листа, вернуть «Вакант» в её прежнее состояние.

## Сценарий 2. Сверка ролей: сначала симуляция, потом боевой режим

Проверяет: безопасный режим не меняет Discord, боевой — приводит роли к данным панели;
Google Таблица не меняется вообще.

**Подготовка:** у бойца «Сокол» в панели звание = **Рядовой**, подразделение = **Танковая рота**.
На тестовом сервере вручную выдайте ему роль **Ефрейтор** (лишняя) и снимите **Рядовой**.

**Шаг 2.1 — симуляция (dry run)**

| Звено | Что происходит |
|---|---|
| Интерфейс | **Обслуживание системы** → «Сверка ролей Discord» → **«Проверить без изменений»** |
| Ожидание | тост **«Проверка завершена — смотрите журнал»**, в карточке — счётчики |
| Postgres | `SELECT kind, title, detail, ok FROM bot_logs ORDER BY id DESC LIMIT 3;` — запись с заголовком **«Сверка ролей (проверка без изменений)»** |
| ШДС | изменений нет |
| Discord | роли **не изменились**: у «Сокола» по-прежнему «Ефрейтор» без «Рядового» |

> Если роли всё-таки поменялись, значит настройка `role_sync_dry_run` = `false`. Проверьте:
> `SELECT key, value FROM bot_settings WHERE key LIKE 'role_sync%';`

**Шаг 2.2 — точечное применение**

| Звено | Что происходит |
|---|---|
| Интерфейс | **«Применить сейчас»** — на тестовом сервере безопасно, бойцов немного |
| Ожидание | тост **«Сверка ролей выполнена»**; в отчёте видно, что сняли «Ефрейтор» и выдали «Рядовой» |
| Postgres | новая запись в `bot_logs`: заголовок **«Роли Discord синхронизированы»** (или «Сверка ролей: расхождений нет»), `category = 'edit'`, детали «Выдано ролей» / «Снято ролей» / «Изменения» |
| ШДС | изменений нет — сверка таблицу не трогает |
| Discord | у «Сокола» появился «Рядовой», исчез «Ефрейтор»; роли **«Отпуск»**, **«Запас»**, модератора и командирского состава не тронуты (защищённый список) |

> ℹ️ Если у «Сокола» в панели **не заполнено подразделение**, снятие лишней роли **не произойдёт** —
> это пятая защита сверки («карточка неполная»). Заполните подразделение и повторите: это
> отдельный проверочный кейс, полезный сам по себе.

Точечная проверка одного бойца (например, бойца с id = 1):

```powershell
curl -X POST "http://localhost:3000/api/admin/maintenance/roles?mode=apply&member=1" --cookie "auth_token=ВАША_COOKIE"
```

**Шаг 2.3 — фоновая сверка (если позволяет время прогона)**

1. Настройки → тумблер **вкл**, интервал `5` минут, «Роли не менять» — снять.
2. Измените звание бойца в панели («Сохранить»), подождите 5–6 минут.
3. Discord: звание сменилось само. В журнале — запись с источником `schedule`.

**Откат:** вернуть тумблеры в исходное состояние (выкл / проверка включена); роли на тестовом
сервере вернуть вручную.

## Сценарий 3. Рапорт об экзамене: закраска столбца, оценка и автоматический «Берет»

Проверяет три вещи сразу: столбец норматива в ШДС, запись оценки в ячейку и автоматическое
закрытие «Берета» с выдачей роли — без перезапуска бота.

**Что где лежит в таблице** (`src/lib/gsheets.ts`, `src/lib/reports.ts`):

| Параметр | Танковая рота | Артиллерийский дивизион |
|---|---|---|
| Колонка имени | `C` | `C` |
| Строка с названиями нормативов | 6 | 8 |
| Блок оценок (экзамены) | `H`–`AE` | `I`–`AG` |
| Диапазон «Добавление в ШДС» | 42–56 | 32–41 |
| Столбец «Берет» | `AE` | `AG` |

Столбец норматива ищется **по заголовку** в строке 6 (рота) или 8 (дивизион), а не по номеру: бот
сопоставляет название из рапорта с заголовком, снимая кавычки и известные опечатки. Если
переименовать заголовок в шапке, отметка молча не встанет — вместо этого в итоге появится
`ВНИМАНИЕ: не найдены в таблице — …` (см. шаг 3.4).

⚠️ **Блок оценок у листов разный** (`examStartCol` / `examEndCol` в `LAYOUTS`, `src/lib/gsheets.ts`):
у роты экзамены начинаются с `H`, у дивизиона — с `I`. Совпадение вне этих границ отбрасывается:
в служебных столбцах листа может стоять слово, совпадающее с названием норматива, и закраска
уехала бы в «Заметки». Оценка при этом пишется **в свой столбец** каждой ячейки: если в рапорте
указаны оценки у нескольких нормативов, они не размножатся по всем закрашенным столбцам.

**Шаг 3.1 — подача рапорта бойцом**

| Звено | Что происходит |
|---|---|
| Интерфейс | войти бойцом (Dev Login → «боец Танковой роты»), `/reports` → **«Подать рапорт»** → тип **«Сдать экзамены / нормативы»** → **блок «Механик - Водитель»** → норматив «Огневая подготовка», оценка **«Хорошо»** → отправить |
| Ожидание | «Рапорт отправлен», статус в списке — «На рассмотрении». В списке нормативов видны **только блоки роты** — ни РСЗО, ни БПЛА предложить нельзя |
| Postgres | `SELECT id, type, status, payload FROM service_reports ORDER BY id DESC LIMIT 1;` — `type = 'exam'`, `status = 'pending'` |
| ШДС | пока ничего |
| Discord | в канал рапортов ушёл Embed с кнопками «Одобрить / Отклонить» (при пустом `reports_channel_id` — в канал ШДС) |

**Шаг 3.2 — одобрение**

| Звено | Что происходит |
|---|---|
| Интерфейс | `/admin/reports` → карточка рапорта → **«Одобрить»** (или кнопка под Embed в Discord) |
| Postgres | `status = 'approved'`, заполнены `reviewed_by` и `reviewed_at` |
| ШДС | ячейка столбца **«Огневая подготовка»** в строке бойца закрашена зелёным и содержит **«Хорошо»** |
| Discord | изменений нет — норматив сам по себе роли не даёт |

> ℹ️ Оценка — это **слово из фиксированного списка** (`EXAM_GRADES` в `src/lib/reports.ts`):
> «Отлично», «Хорошо», «Удовлетворительно», «Неудовлетворительно». Ввести «4» не получится —
> валидатор отклонит. У базового норматива **КМБТ** оценки нет вовсе (`graded: false`), и в ячейку
> попадёт только закраска.

Проверка: откройте копию таблицы, лист «Танковая рота», строка бойца; нужная ячейка зелёная,
в ней «Хорошо». Сквозная сверка: `npm run verify:sheet`.

**Шаг 3.3 — «Берет» закрывается сам**

Нужны **все четыре** норматива: **Топография**, **Связь**, **Строевая подготовка**,
**Должностные лица** (`BERET_EXAM_CODES`). Их можно подать четырьмя рапортами или одним — бот
учитывает и ранее одобренные, и текущий.

| Звено | Что происходит |
|---|---|
| Интерфейс | `/exams` → вкладка «Экзамен на берет»: четыре норматива зелёные и строка **«Берет»** тоже зелёная |
| Postgres | четыре рапорта `approved`, у каждого заполнен `payload.exams[].exam_code` |
| ШДС | закрашены четыре столбца нормативов **и** столбец **«Берет»** (`AE` / `AG`) |
| Discord | роль **«Берет»** выдана сразу при одобрении последнего рапорта — без перезапуска и без сверки |

В журнале (**Журнал** → «Редактирование») в итоге рапорта будет `выдана роль «Берет»`.
Варианты сообщений-заменителей говорят сами за себя:
`роль «Берет» на сервере не найдена — выдайте её вручную` (нет `beret_role_id` и нет роли с
именем «Берет»), `guild_id не задан — роль «Берет» не выдана`.

**Шаг 3.4 — негативная проверка (необязательно)**

Переименуйте в **копии** таблицы заголовок «Связь» на «Связь-ТЕСТ» и одобрьте рапорт по этому
нормативу. Ожидание: рапорт одобрен, в итоге предупреждение
`ВНИМАНИЕ: не найдены в таблице — Связь`, столбец пуст. Так проверяется, что молчаливый отказ
превратился в явное сообщение. **Верните заголовок как был.**

**Откат:** `UPDATE service_reports SET status = 'pending', reviewed_by = NULL WHERE id IN (…);`
и очистить закраску ячеек (ПКМ → «Очистить» → «Формат») в копии таблицы.

**Шаг 3.5 — «Берет» как ворота допуска на РСЗО (проверяется на дивизионе)**

Это лучший тест связки «нормативы → ступень → допуск», потому что «Берет» здесь реально
что-то запрещает.

1. Войдите бойцом **Артиллерийского дивизиона** (Dev Login → «наводчик Артдивизиона»).
2. Откройте `/exams`. До сдачи берета вкладка **«Допуск на РСЗО»** помечена замком, а внутри —
   текст **«Требуется сдача Экзамена на берет»**. Это `beretGate` в `src/lib/exams.ts`:
   нормативы у бойца могут быть сданы, но допуск не выдаётся.
3. Сдайте четыре норматива берета (те же: Топография, Связь, Строевая подготовка,
   Должностные лица) и одобрьте рапорты.
4. `/exams` → замок с «Допуск на РСЗО» снят. Проверьте, что остальные ступени дивизиона
   (**«Допуск на Минометы»**, **«Допуск на САУ + Гаубицы»**) при этом не сломались.

| Звено | Что происходит |
|---|---|
| Интерфейс | замок исчез, вкладка открылась |
| Postgres | те же четыре рапорта `approved` |
| ШДС | закрашены нормативы и столбец «Берет» (`AG` у дивизиона) |
| Discord | роль «Берет» выдана |

Обратная проверка: верните последний рапорт берета в статус «На рассмотрении»
(`UPDATE service_reports SET status = 'pending' WHERE id = <id>;`) — вкладка РСЗО должна снова
заблокироваться.

> ℹ️ **Важное уточнение про источник данных.** Раздел «Экзамены» и сверка ролей определяют
> сдачу норматива **по одобренным рапортам в базе**, а не по закраске ячеек в таблице
> (`/api/member/dossier` → `collectQualificationDetails`, `loadBeretPassed` в
> `src/lib/role-sync-runtime.ts`). Закраска в ШДС — это следствие решения штаба, а не его источник.
> Поэтому «стереть закраску в таблице, чтобы проверить реакцию интерфейса» бессмысленно: интерфейс
> её не читает — откатывайте статус рапорта.

## Сценарий 4. Канал запросов ролей: выдача ролей по реакции

Проверяет самый чувствительный путь: изменение ролей живым людям по сообщению в Discord,
с разграничением прав «экзаменатор / модератор».

**Формат сообщения в канале `roles_channel_id`** (`parseRoleRequest`, `parseRoleCommand`):

```
@Сокол
@Волков
Выдать Ефрейтор ТР, Выдать Игроман, Снять Новобранец
```

- первая строка — обязательна: получатель ролей (упоминание);
- вторая строка — необязательна: экзаменатор (тоже упоминание), именно он (или модератор)
  вправе подтвердить заявку реакцией;
- далее строки команд. Действия — **Выдать** / **Снять**; между ними запятая. Если действие не
  указано, по умолчанию **выдать**. Служебное слово «роль» можно опускать;
- «Ефрейтор ТР» — составное имя: бот разберёт его на направление ТР + звание + общие роли
  (Корпус, категория «Звания») и снимет «Новобранца»/«Друга АТК».

> ⚠️ **Операция выполняется целиком или не выполняется вовсе.** `applyRoleCommand` сначала
> проверяет **все** роли из строки, и если хотя бы одна не найдена или защищена — вся заявка
> отклоняется, ни одна роль не выдаётся. Поэтому в шаблоне выше нельзя вставить заведомо
> несуществующее имя и ждать, что отработает остальное.

**Шаг 4.1 — публикация запроса**

| Звено | Что происходит |
|---|---|
| Интерфейс | напишите сообщение по шаблону в канал запросов ролей |
| Postgres | пока ничего |
| ШДС | ничего |
| Discord | в консоли бота: `[bot] Запрос ролей: <@…> ← выдать Ефрейтор ТР (экзаменатор <@…>)` |

**Шаг 4.2 — реакция не того человека**

| Звено | Что происходит |
|---|---|
| Интерфейс | поставьте реакцию ✅ **не** экзаменатором и не модератором |
| Ожидание | реакция снимается, в ветке появляется «подтвердить запрос ролей может только упомянутый экзаменатор или модератор» |
| Discord | роли **не изменились** |

**Шаг 4.3 — подтверждение**

| Звено | Что происходит |
|---|---|
| Интерфейс | экзаменатор или модератор ставит ✅ (или 🟢 / :ATK:) |
| Discord | сообщение помечено `[ОДОБРЕНО]`; роли выданы/сняты; под сообщением — ветка с итогом |
| Postgres | `SELECT category, action, details FROM bot_logs WHERE kind = 'roles' ORDER BY id DESC LIMIT 1;` — детали: «Получатель», «Экзаменатор», «Операции», «Итог» |
| ШДС | ничего — канал ролей таблицу не трогает |

Отказ: реакция ❌ — сообщение помечается `[ОТКАЗАНО]`, роли не меняются.

**Негативные проверки, обязательные к прогону (каждая — отдельным сообщением):**

| Что вводим | Ожидание |
|---|---|
| `Выдать Модератор` | `«Модератор» — выдавать/снимать эту роль запрещено`, роли не изменены (`PROTECTED_ROLE_NAMES`) |
| `Выдать Несуществующая` | `«Несуществующая» — роль не найдена на сервере`, роли не изменены |
| `Выдать Ефрейтор ТР, Выдать Несуществующая` | **обе** операции отклонены: ни одна роль не выдана |
| сообщение без упоминания получателя | заявкой не считается, бот игнорирует |
| одна строка (без команды) | игнорируется: `parseRoleRequest` требует минимум две строки |
| получателя нет на сервере | «Не удалось найти участника … — роли не изменены» |

**Откат:** снять выданные вручную роли, `DELETE FROM bot_logs WHERE kind = 'roles' AND id = …;`
(или оставить — журнал и есть подтверждение прогона).

## Сценарий 5. Отпуск и запас: рапорты из кабинета

Оба сценария проверяют связку «кабинет бойца → БД → роль Discord» и **не трогают Google Таблицу**
(важно: заявку на отпуск `applyShdsRequest` отклонит с сообщением
«Заявка на отпуск обрабатывается не в таблице» — это проверка того, что пути не перепутаны).

**Шаг 5.1 — рапорт на отпуск**

| Звено | Что происходит |
|---|---|
| Интерфейс | боец → `/reports` → «Подать рапорт» → тип **«Рапорт на отпуск»** → даты «с» и «по» (`ГГГГ-ММ-ДД`), причина (2+ символа) → отправить |
| Postgres | `service_reports`: `type = 'vacation'`, `payload = {from, to, reason}`, `status = 'pending'` |
| ШДС | ничего |
| Discord | Embed в канал рапортов с кнопками «Одобрить / Отклонить» |

Проверка валидации (обязательно): дата «по» раньше даты «с» → ошибка
`Рапорт на отпуск: дата возвращения раньше даты начала`; пустая причина → `Рапорт на отпуск: укажите причину`.

**Шаг 5.2 — одобрение рапорта на отпуск**

| Звено | Что происходит |
|---|---|
| Интерфейс | модератор → «Одобрить» (в панели или кнопкой в Discord) |
| Postgres | у бойца `vacation = true`, `vacation_until` = дата «по» в 00:01 МСК, `status = 'vacation'`, `vacation_notified = false` |
| ШДС | ничего |
| Discord | выдана роль **«Отпуск»** (`leave_role_id`), бойцу ушло ЛС об одобрении |

Проверка в кабинете: боец в отпуске **исключён из пингов на операцию** и подсвечен в `/members`
как «в отпуске».

Автоснятие отпуска (`checkVacations` в `src/lib/bot.ts`): бот раз в минуту проверяет
`vacation_until`. Когда время наступило — снимает роль «Отпуск», чистит поля и пишет в канал
отпусков «твой отпуск подошел к концу». Чтобы проверить это без ожидания, поставьте дату
«по» = **сегодня** и одобрьте рапорт: следующий тик (в течение минуты) закроет отпуск сам.

**Шаг 5.3 — уход в запас**

| Звено | Что происходит |
|---|---|
| Интерфейс | боец → `/reports` → «Подать рапорт» → тип **«Перевод в резерв»** → причина → отправить; модератор одобряет |
| Postgres | `active = false`, `status = 'dismissed'`, кабинет закрыт |
| ШДС | строка бойца целиком (колонки **A–AG**) уезжает на лист **«Запас»**; в служебных колонках: **AH** — подразделение, **AI** — сохранённые Discord-роли, **AJ** — дата ухода. Записи, сделанные до расширения снапшота, читаются по-прежнему: их служебные данные лежат в **U–W**. На листе подразделения строка зачищается шаблоном «Вакант» |
| Discord | с бойца снимаются **все** роли, кроме `@everyone`, и выдаётся роль **«Запас»** (`reserve_role_id`) |

Возврат из запаса (заявка «Возврат из запаса»): строка возвращается на лист подразделения
вместе со всеми отметками A–AG, роль «Запас» снимается, а ранее сохранённые роли
восстанавливаются из колонки **AI** (у записей старого формата — из **V**).

**Откат:** для отпуска — `UPDATE division_members SET vacation = false, vacation_until = NULL,
vacation_notified = false, status = 'active' WHERE id = <id>;` и снять роль «Отпуск»; для
запаса — вернуть бойца через заявку «Возврат из запаса» (штатный путь) и удалить тестовую строку
с листа «Запас».

## Сценарий 6. Обслуживание: синхронизация ШДС, резервная копия, очистка

Все три действия — на вкладке **Настройки** → блок **Обслуживание системы**
(`src/components/maintenance-panel.tsx`). Они выполняются сразу, без кнопки «Сохранить».

| Действие | Роут | Что проверить |
|---|---|---|
| **Синхронизировать сейчас** | `POST /api/admin/maintenance/sync` | ответ `{ ok: true, message: "Синхронизация с Google Таблицей завершена", sync: { updated, sheets, detail, status } }`; в карточке обновилось «Последняя: …»; в журнале — запись `kind = 'sync'` |
| **Создать резервную копию** | `POST /api/admin/maintenance/backup` | тост об успехе; в карточке появился новый файл с датой и размером |
| **Очистить устаревшие данные** | `POST /api/admin/maintenance/prune` | удалены просроченные сессии и устаревшие записи журнала; в журнале — запись с числом удалённых |

Проверка синхронизации по цепочке:

| Звено | Что происходит |
|---|---|
| Интерфейс | «Синхронизировать сейчас» |
| Postgres | звание и подразделение бойцов **обновляются из таблицы** (`syncShdsRoster`): `SELECT id, name, rank, unit FROM division_members ORDER BY id;`. В `bot_logs` — свежая запись `kind = 'sync'` |
| ШДС | таблица **не меняется**: синхронизация только читает колонку имён и колонку званий слева от неё |
| Discord | роли не меняются — за них отвечает сверка (сценарий 2) |

Что здесь стоит проверить руками: направление данных. Поменяйте в копии таблицы звание бойца,
нажмите «Синхронизировать сейчас» — в панели на `/members` звание должно подтянуться из таблицы
(**таблица — источник истины по званиям**; rs-red.com обновляет только онлайн). Записи вида
`Предупреждения: лист «…» не найден` в деталях означают, что лист подразделения назван иначе —
это ровно та ошибка, которую ловит шаг 1.3.

> Синхронизация состава с rs-red.com (`/api/sync`, задача планировщика) — **другая** операция: она
> обновляет часы онлайна и помечает неактивными бойцов, исчезнувших из состава на сайте. Локальные
> поля панели (`discord_id`, `vacation`, `warnings`) при этом сохраняются.

Расписание (чтобы понимать, что бот делает сам):

- синхронизация ШДС — раз в час;
- резервная копия и очистка — раз в сутки;
- отпуска — раз в минуту;
- фоновая сверка ролей — по настройке `role_sync_interval_min` (по умолчанию 30 минут);
- **контроль ролей исключённых — раз в 30 минут** (`roles-monitor:<слот>` в `src/lib/scheduler.ts`).

## Сценарий 7. VIP-техника и уровни доступа в кабинете бойца

Проверяет матрицу техники [`src/lib/vehicles.ts`](src/lib/vehicles.ts:1) и её отображение в
[`src/components/dossier-panel.tsx`](src/components/dossier-panel.tsx:605): фильтр по уровню VIP,
бейджи и правило `stricterRank` (более строгое из двух званий).

**Что откуда берётся:**

| Понятие | Значение в коде | Где учитывается |
|---|---|---|
| Уровень VIP | `vipTier`: `0` — «Базовая», `1` — «VIP 1», `2` — «VIP 2» | бейдж на карточке, фильтр кабинета |
| Кнопки фильтра | `VEHICLE_VIP_FILTERS` = `all · base · vip1 · vip2` | порядок «Все · Базовая · VIP 1 · VIP 2» |
| Итоговое требование по званию | `stricterRank(звание ступени, vehicle.requiredRank)` | допуск к единице техники |
| Пометка «мин. звание» из реестра | `vehicle.requiredRank` | бейдж звания на карточке |

Ключевые примеры из матрицы (сверены с реестром гаража):

| Техника | Ступень матрицы | `requiredRank` | `vipTier` | Итоговый порог |
|---|---|---|---|---|
| Т-72Б (1985) (RHS) | Рядовой | `null` | 0 | **Рядовой** (ступень) |
| 2С6 «Тунгуска» | Ефрейтор | Ефрейтор | 1 | **Ефрейтор** |
| БМП-3М | Мл. Сержант | Мл. Сержант | 1 | **Мл. Сержант** |
| Т-80У (RED) | Ст. Сержант | Ст. Сержант | 1 | **Ст. Сержант** |
| Т-90СМ (объект 188СМ) (RHS) | Старшина | Старшина | 1 | **Старшина** |
| Т-80УЕ-1 (RED) | Прапорщик | Прапорщик | 2 | **Прапорщик** |
| Т-90М (RED) | Лейтенант | Лейтенант | 0 | **Лейтенант** |
| Т-90М «Прорыв» (Proryv-3) | Лейтенант | Лейтенант | 2 | **Лейтенант** |
| Т-90MS Tagil | Лейтенант | Лейтенант | 1 | **Лейтенант** |
| Т-14 Армата | Ст. Лейтенант | Ст. Лейтенант | 2 | **Ст. Лейтенант** |
| Т-100 «Чёрный Орёл» (Ивентолог) | Лейтенант | `null` | 0 | **Лейтенант**; цена `null` → «по решению штаба» |

> ℹ️ **Зачем `stricterRank`.** Порог единицы техники — не всегда порог ступени. У базовых машин
> требование задаёт ступень матрицы, но у части реестра «мин. звание» названо прямо в карточке.
> Берётся **более высокое** из двух званий (по позиции в `RANKS`, не по алфавиту): если машину
> однажды переставят в другую ступень, допуск не станет мягче случайно. Именно поэтому Т-90М
> при звании «Сержант» честно показывает «Требуется повышение», хотя стоит в лейтенантской ступени.

**Шаг 7.1 — фильтр «Все / Базовая / VIP 1 / VIP 2»**

| Звено | Что происходит |
|---|---|
| Интерфейс | войти бойцом Танковой роты → `/profile` → карточка **«Техника»**; над списком — четыре кнопки-фильтра со счётчиками |
| Ожидание | кнопки идут строго в порядке **Все · Базовая · VIP 1 · VIP 2**; активная кнопка окрашена в цвет своего уровня: VIP 1 — янтарный, VIP 2 — пурпурный, «Все» и «Базовая» — фирменный бордовый |
| Postgres | запросов нет: фильтр считается на клиенте |
| Discord | изменений нет |

**Что проверить руками (каждый пункт — отдельная проверка):**

1. **Счётчики** совпадают с числами на вкладках: сумма `Базовая + VIP 1 + VIP 2` равна числу на
   активной вкладке («Доступная техника» или «Требует сдачи / повышения»).
2. **Счётчики считаются по текущей вкладке, а не по всему реестру.** Переключите вкладку и
   убедитесь, что числа на кнопках фильтра изменились. Это намеренно
   (`vipFilterCounts`): счётчик «Базовая (12)» рядом с пустым списком читался бы как ошибка
   фильтра.
3. **Фильтр не сбрасывает вкладку.** Выберите вкладку «Требует сдачи / повышения», затем
   «VIP 2» — вкладка остаётся той же. Уровень VIP живёт отдельным состоянием и вкладку не
   переключает.
4. **Пустое пересечение говорит правду.** Если в выбранной вкладке нет техники выбранного
   уровня, показывается текст **«В этой категории техники нет — переключите уровень VIP или
   вкладку.»** (а не «Пока ничего не открыто» — тот текст оставлен для действительно пустого
   списка, когда `counts.all === 0`).

**Шаг 7.2 — бейджи званий и VIP**

| Звено | Что происходит |
|---|---|
| Интерфейс | в карточке техники рядом с названием — бейдж **VIP** и, если у единицы задано «мин. звание», бейдж звания |
| Ожидание | «Базовая» техника бейдж VIP **не рисует** — там нечего сообщать (`VipBadge` при `tier === 0` возвращает `null`) |
| Postgres | запросов нет |

Проверьте на конкретных карточках:

- «Т-72Б (1985) (RHS)» — бейджа VIP нет, бейджа звания нет (порог задаёт ступень);
- «2С6 «Тунгуска»» — бейдж **VIP 1** и бейдж **Ефрейтор**;
- «Т-90М (RED)» — бейджа VIP нет (базовая машина), но бейдж **Лейтенант** есть: цена 450;
- «Т-14 Армата» — бейдж **VIP 2** и бейдж **Ст. Лейтенант**.

**Шаг 7.3 — отсечка `stricterRank` (ключевой кейс)**

Проверяется на бойце Танковой роты со **званием «Сержант»**.

| Звено | Что происходит |
|---|---|
| Интерфейс | `/profile` → вкладка **«Требует сдачи / повышения»** |
| Ожидание 1 | **Т-90М (RED)** находится в **запертых**, хотя стоит в ступени «Лейтенант», а «мин. звание» у него — Лейтенант: карточка говорит «Требуется повышение», в `missing` — `звание Лейтенант` |
| Ожидание 2 | техника ступеней Рядовой…Сержант — в **доступных**: Т-72Б3 (RED), Т-90СА (RHS), БМП-3 (VВесна-К/ДБ) |
| Ожидание 3 | верхние ступени (Ст. Сержант, Старшина, Прапорщик, Лейтенант, Ст. Лейтенант) помечены как запертые, и в предпросмотре «Откроется на звании …» показана **ближайшая** ступень, а не самая богатая |
| Postgres | ничего не меняется: отчёт считается из карточки бойца и одобренных рапортов |
| Discord | изменений нет — матрица техники роли не выдаёт |

> ℹ️ Порядок «ближайшей ступени» считается по позиции звания в `RANKS`, а не по порядку в
> матрице (`nextTankTier`). Иначе «Прапорщик» (у него в матрице одна машина) считался бы
> следующей ступенью после «Старшины», и лейтенантская техника «терялась» бы из предпросмотра.

**Шаг 7.4 — артиллерия: допуск по нормативам, а не по званию**

> нормативами получит категорию целиком.

| Интерфейс | боец без подразделения (`unit = NULL`) → `/profile` |

**Откат:** сценарий ничего не меняет — откатывать нечего. Достаточно вернуть бойцу прежнее

## Сценарий 8. Контроль ролей Discord у исключённых (Roles Monitor)

Проверяет задачу [`runDismissedRolesCheck`](src/lib/tasks.ts:600) и её правила
[`src/lib/roles-monitor.ts`](src/lib/roles-monitor.ts:1). Смысл задачи: боец переведён в статус
`dismissed`, но роль подразделения на сервере осталась — пока её не снимут, исключённый читает
закрытые каналы. Роли снимает живой человек, поэтому через сутки комсоставу нужен пинг.

**Как работает (важно понять до теста):**

| Правило | Реализация | Что это значит на стенде |
|---|---|---|
| Кто кандидат | `status = 'dismissed'` | активный боец роль имеет по праву |
| Отсчёт срока | `dismissed_at` + `roles_monitor_delay_hours` (по умолчанию 24 ч) | `updated_at` **не** используется: его меняет любая правка карточки |
| Однократность | `roles_alert_sent_at IS NULL` | флаг ставится даже когда роли уже сняты — иначе задача вечно возвращалась бы к тому же бойцу |
| Нужен ID | `discord_id` похож на снежинку (`/^\d{5,25}$/`) | строка `manual` или пустое значение не считается |
| Что пингуем | роль АТК (`COMMON_ROLE_IDS.ATK_CORPS`) всё ещё у бойца | «Друг АТК» снимать не требуем — иначе уведомление приходило бы почти на каждого |

**Шаг 8.1 — условия 24 часов: «рано» и «пора»**

Подготовьте бойца прямо в базе (быстрее, чем ждать сутки):

```sql
-- Боец исключён 1 час назад и имеет Discord ID тестового аккаунта:
UPDATE division_members
   SET status = 'dismissed',
       dismissed_at = NOW() - INTERVAL '1 hour',
       roles_alert_sent_at = NULL,
       discord_id = '<ID_ТЕСТОВОГО_УЧАСТНИКА>'
 WHERE id = <id>;
```

| Проверка | Ожидание |
|---|---|
| исключён 1 час назад, срок 24 ч | напоминания **нет**; в журнале при отсутствии других кандидатов — строка «Проверено исключённых: 0. Напоминаний не требуется.» |
| `dismissed_at = NOW() - INTERVAL '25 hours'` | напоминание **есть** (следующий цикл — до 30 минут) |
| `dismissed_at IS NULL`, статус `dismissed` | напоминания **нет**: «момент исключения неизвестен» — отсчитывать не от чего |
| `roles_alert_sent_at` заполнен | напоминания **нет**, даже если роль всё ещё висит |

Ускорить прогон можно настройкой: поставьте `roles_monitor_delay_hours = 1` и `dismissed_at`
на два часа назад — задача сработает по укороченному сроку. В интерфейсе поле принимает только
цифры, допустимый диапазон — 1…720.

**Шаг 8.2 — проверка отсечки по ролям (что пингуется, что нет)**

| Ситуация с ролями у исключённого | Ожидание |
|---|---|
| висит роль **АТК** — «Артиллерийско-Танковый Корпус» (`COMMON_ROLE_IDS.ATK_CORPS`) | Embed **«⚠️ Контроль личного состава // Не сняты роли»** в канал уведомлений + пинг роли комсостава |
| роли сняты полностью | напоминания **нет**; в консоли `[roles-monitor] <id>: роли подразделения уже сняты` |
| у бойца осталась только **«Друг АТК»** | напоминания **нет**: это роль бывшего бойца, требовать её снятия нельзя |
| участника нет на сервере (404) | напоминания **нет**; в консоли `[roles-monitor] <id>: участник не найден на сервере — роли неактуальны`. Это НЕ «роли сняты», но и не повод для пинга |
| остались другие роли клана (звания, подразделение) | пинг **есть**, а в деталях журнала перечислены все оставшиеся роли клана, не только АТК |

Текст Embed (проверяется глазами и по журналу):

```
Заголовок: ⚠️ Контроль личного состава // Не сняты роли
Описание:  Боец <Позывной> (<@discord_id>) покинул подразделение более 24 часов назад,
           но до сих пор имеет роль АТК на сервере.
           Пожалуйста, снимите роли подразделения.
Поля:      «Исключён» — <t:…:R>, «Осталось ролей подразделения» — число
Футер:     Проверка ролей исключённых · напоминание отправляется однократно
```

**Шаг 8.3 — изоляция сбоев API Discord (404 / 429)**

Каждый боец обрабатывается в **своём** `try`: ошибка одного запроса не должна ронять проверку
остальных, иначе один ушедший с сервера боец заблокировал бы напоминания всем, кто идёт после
него в выборке.

| Что имитируем | Как | Ожидание |
|---|---|---|
| **404** — участника нет на сервере | задайте бойцу `discord_id` несуществующего пользователя (например `123456789012345678`) | задача продолжается; в консоли `участник не найден на сервере — роли неактуальны`; `roles_alert_sent_at` всё равно проставляется; в `bot_logs` ошибки нет |
| **429** — лимит Discord | подготовьте 2–3 кандидатов, поставьте `discord_queue_*` с малым лимитом (Настройки → очередь Discord), либо запустите задачи конкурентно | запрос проходит через общую очередь [`src/lib/discord-queue.ts`](src/lib/discord-queue.ts:1): она выдерживает `Retry-After` и повторяет попытку; при исчерпании повторов запись об ошибке попадает в журнал, а **остальные бойцы обрабатываются** |
| сеть/таймаут | остановите доступ к Discord (например, временно неверный токен в настройках) | `errors++` по каждому бойцу, в журнале — «Ошибка проверки ролей исключённого» с Discord ID; задача завершается, а не падает |

Проверьте особый порядок в коде: **`roles_alert_sent_at` ставится и при снятых ролях, и при
отсутствии участника, но НЕ ставится при ошибке запроса.** Поэтому после сетевого сбоя боец
останется кандидатом и будет проверен в следующий цикл — это правильное поведение.

**Шаг 8.4 — логирование в `bot_logs`**

| Звено | Что происходит |
|---|---|
| Интерфейс | **Журнал** → вкладка **«Сайт» (системные)** → подфильтр с `kind = 'roles-monitor'` |
| Postgres | `SELECT created_at, kind, title, detail, ok, error FROM bot_logs WHERE kind = 'roles-monitor' ORDER BY id DESC LIMIT 10;` |
| ШДС | изменений нет |
| Discord | Embed + пинг роли комсостава |

Ожидаемые записи:

| Заголовок | Когда появляется | `ok` |
|---|---|---|
| «Не сняты роли подразделения» | отправлено напоминание по конкретному бойцу | `true` |
| «Ошибка проверки ролей исключённого» | Discord/сеть подвели | `false`, с текстом ошибки |
| «Контроль ролей исключённых» | итог цикла, только если были напоминания или ошибки | `true`, если ошибок не было |

Пример детали успешной записи: `Сокол (Discord 123456789012345678): роли подразделения не
сняты более 24 часов. Роли: 1392226832274948207`.

> ℹ️ **Упоминание бойца работает, а уведомление — нет.** В Embed есть `<@id>`, но
> `allowed_mentions` явно выключает пользователей (`parse: []`, `users: []`) и разрешает только
> роль комсостава. Так исключённого не пингуют, но командир может щёлкнуть по упоминанию и
> сразу открыть профиль того, кому снимать роли.

**Откат:**

```sql
UPDATE division_members
   SET status = 'active', active = true,
       dismissed_at = NULL, roles_alert_sent_at = NULL
 WHERE id = <id>;
DELETE FROM bot_logs WHERE kind = 'roles-monitor' AND id IN (…);
```

**Шаг 8.5 — быстрый прогон через штатный путь исключения (проверка `statusTrackingFields`)**

Ручной `UPDATE` проверяет правила, но не проверяет, что **сама панель** проставляет момент
исключения. Прогоните штатный путь:

1. Боец подаёт рапорт **«Перевод в резерв»**, модератор одобряет.
2. Проверьте: `SELECT status, active, dismissed_at, roles_alert_sent_at FROM division_members WHERE id = <id>;`
   — статус `dismissed`, `dismissed_at` заполнен, `roles_alert_sent_at` пуст.
3. **Ключевая проверка:** сохраните карточку бойца ещё раз, не меняя статус (например, поправьте
   примечание). `dismissed_at` **не должен сдвинуться** — иначе отсчёт 24 часов начинался бы
   заново от любой правки, и напоминание откладывалось бы бесконечно.
4. Верните бойца в строй (возврат из запаса) — `dismissed_at` и `roles_alert_sent_at`
   **обнуляются**, чтобы при следующем исключении отсчёт начался заново.

## Сценарий 9. Полное удаление профиля бойца (только администратор)

Необратимая операция: [`src/lib/member-deletion.ts`](src/lib/member-deletion.ts:1),
роут [`DELETE /api/admin/members/[id]`](src/app/api/admin/members/[id]/route.ts:263) и окно
подтверждения [`src/components/member-delete-button.tsx`](src/components/member-delete-button.tsx:40).

**Шаг 9.1 — права: строго `admin`**

Правило в одной функции (`memberDeletionDecision`): `admin` в **любой** из двух сессий —
панели или кабинета — допускается; вошедший без `admin` получает **403**; без сессии вовсе —
**401**.

| Кто | Как получить сессию | Ожидание |
|---|---|---|
| гость | открыть `/members` в приватном окне | кнопки-корзины нет; прямой `DELETE` → **401** «Нет доступа: авторизуйтесь» |
| **командир подразделения** | Dev Login → «Войти как Волков Д. В. (Командир)» | **403** «Недостаточно прав: удаление профиля доступно только администратору». Правка состава (Discord ID, отпуск) у командира при этом **работает** — это разные полномочия |
| **офицер** | сессия с ролью `officer` | **403**, тот же текст |
| сам боец | Dev Login → «боец Танковой роты» | **403** |
| администратор | сессия `admin` | **200** и удаление |

Проверка «настоящего» 403 (роут считает роль из БД, а не по строке на клиенте):

```powershell
curl -X DELETE "http://localhost:3000/api/admin/members/7?confirmation=Сокол" --cookie "auth_token=ВАША_COOKIE_КОМАНДИРА"
```

| Ожидание по шагам роута | Код |
|---|---|
| нет сессии | 401 |
| сессия есть, роли `admin` нет | 403 |
| запрос с чужого сайта (CSRF) | 403 «Запрос с чужого источника отклонён» |
| id не целое (`7.5`, `7abc`, `0`, `-5`) | 400 «Некорректный ID бойца» |
| бойца нет | 404 «Боец не найден» |
| подтверждение не совпало | 400 «Подтверждение не совпадает: введите позывной бойца, чтобы удалить профиль» |

> ⚠️ **Дробный адрес не должен удалять соседа.** `Number.parseInt('7.5')` вернул бы `7`, и промах
> в адресе удалял бы **чужой** профиль. Роут использует строгий `parseMemberId`: принимаются
> только целые положительные значения без хвостов.

> ℹ️ **Почему 403, а не 401.** Код ответа должен соответствовать реальности: иначе командир,
> потерявший права, будет искать проблему в cookie вместо роли.

**Шаг 9.2 — модальное окно с вводом позывного**

| Звено | Что происходит |
|---|---|
| Интерфейс | `/members` → колонка **«Действия»** → красный значок корзины |
| Ожидание 1 | открывается окно с предупреждением (красная рамка, `role="dialog"`, заголовок «состав // удаление профиля»), текст «Вы действительно хотите удалить профиль бойца …? Это действие необратимо: будут удалены допуски, история и привязка к Discord» |
| Ожидание 2 | кнопка **«Удалить безвозвратно»** заблокирована (`disabled`), пока ввод не совпал с позывным |
| Ожидание 3 | поле подписано `Для подтверждения введите «<позывной>»`; сравнение нечувствительно к регистру и лишним пробелам |
| Ожидание 4 | если позывного у бойца нет, подтверждением служит **имя из табеля** — в окне показано именно оно |
| Ожидание 5 | закрытие: клик по фону, «Отмена», `X` или `Escape`; во время удаления окно не закрывается |

> ⚠️ **Совпадение ищется на двух уровнях.** Окно — удобство, а не защита: проверка
> подтверждения выполняется **и на сервере**, поэтому случайный `DELETE` из консоли или скрипта
> карточку не сотрёт. Подтверждение можно передать как телом `{"confirmation":"Сокол"}`, так и
> параметром `?confirmation=Сокол`.

**Шаг 9.3 — что происходит с данными (одна транзакция)**

Перед проверкой зафиксируйте исходное состояние:

```sql
SELECT id, name, callsign FROM division_members WHERE id = <id>;
SELECT id, username, member_id FROM users WHERE member_id = <id>;
SELECT count(*) FROM member_sessions WHERE member_id = <id>;
SELECT count(*) FROM weekly_stats     WHERE member_id = <id>;
SELECT count(*) FROM service_reports      WHERE member_id = <id>;
SELECT count(*) FROM recruit_applications WHERE member_id = <id>;
```

Затем удалите профиль и повторите запросы.

| Шаг | Что делается | Как убедиться |
|---|---|---|
| 1 | боец найден в `division_members` (иначе 404) | — |
| 2 | **`users.member_id = NULL`** — учётная запись панели отвязывается | вход в панель **не ломается**; в `users` строка осталась, `member_id` пуст |
| 3 | удалены **все сессии кабинета** бойца из `member_sessions` | `member_token` бойца перестаёт работать сразу; открытая вкладка кабинета при следующем запросе уводит на вход |
| 4 | удалены снимки недельной статистики (`weekly_stats`) | это технический потомок бойца, а не документ |
| 5 | очищены зависимые таблицы со **строгими** внешними ключами (список берётся из `pg_constraint`, а не угадывается) | `DELETE` не падает на FK даже в базе, обновлённой вручную |
| 6 | удалена сама строка `division_members` | бойца нет в табеле, панель обновила таблицу без перезагрузки |
| 7 | запись в `bot_logs` **после** фиксации транзакции | внутри транзакции её стёр бы откат |

> ⚠️ **Рапорты и заявки сохраняются (SET NULL).** `service_reports` и `recruit_applications`
> **не удаляются**: внешние ключи переведены на `ON DELETE SET NULL` (миграция
> [`scripts/migrations/2026-09-member-profile-delete.sql`](scripts/migrations/2026-09-member-profile-delete.sql:1)),
> а позывной в них продублирован текстовой колонкой. Проверка после удаления:
>
> ```sql
> SELECT conname, confdeltype FROM pg_constraint
>  WHERE conname IN ('service_reports_member_id_division_members_id_fk',
>                    'recruit_applications_member_id_division_members_id_fk');
> -- ожидается 'n' (SET NULL) у обоих.
> -- 'c' — история стиралась бы молча; 'a' — удаление падало бы на ограничении.
> ```
>
> Проверьте руками: рапорт удалённого бойца **остался** в `/admin/reports` с `member_id = NULL`,
> позывной и решение модератора читаются.

**Шаг 9.4 — запись в журнал и ответ API**

| Звено | Что происходит |
|---|---|
| Интерфейс | **Журнал** → вкладка **«Редактирование»** → запись **«Удаление профиля бойца»** |
| Ожидание интерфейса | тост об успехе, строка исчезает из таблицы |
| Postgres | `SELECT author, action, details, title, ok FROM bot_logs WHERE title = 'Удаление профиля бойца' ORDER BY id DESC LIMIT 1;` |

Ожидаемые поля записи:

| Поле | Значение |
|---|---|
| `category` / `kind` | `edit` / `system` |
| `author` | `Администратор <логин панели>` |
| `action` | `удалил личное дело бойца <позывной> (ID: <id>)` |
| `detail` | `Личное дело бойца <ФИО> удалено безвозвратно` |
| `details` | «Боец», «Позывной», «ID», «Сессии кабинета», «Снимки статистики», «Отвязано учётных записей» |
| `ok` | `true` |

Ответ API успешного удаления (`200`):

```json
{
  "ok": true,
  "member": { "id": 7, "name": "…", "callsign": "Сокол" },
  "removed": { "sessions": 2, "weeklyStats": 1, "unlinkedPanelAccounts": 1 },
  "message": "Личное дело бойца Сокол удалено безвозвратно"
}
```

**Негативные проверки:**

| Ситуация | Ожидание |
|---|---|
| удалить бойца дважды | второй запрос → **404**: «успех» на несуществующем id маскировал бы опечатку в адресе |
| журнал недоступен (сбой записи в `bot_logs`) | удаление **не откатывается**: в консоли `[admin/members] Удаление прошло, но запись в журнал не удалась: …`, клиент получает `ok: true` — профиля действительно больше нет |
| ошибка базы внутри транзакции | `500` с текстом «Не удалось удалить профиль бойца. Обратитесь к логам сервера.»; имена таблиц и фрагменты SQL клиенту **не показываются** |
| бойца удалили параллельно | срабатывает `MemberDeletionError('not_found')` → **404**, транзакция откатывается |

**Откат:** полноценного отката нет — операция необратима. Восстанавливайте из резервной копии
(раздел 3.3.1) либо создайте бойца заново через `/admin/recruits`. Поэтому тестируйте удаление
**на тестовом бойце** и **после снятия резервной копии**.

## Сценарий 10. Безопасность и продакшен-окружение

Четыре независимые проверки: секреты-заглушки, локальный порт БД, healthcheck контейнера,
индексы после миграции.

**Шаг 10.1 — защита от дефолтных секретов**

Проверяется [`getJwtSecret`](src/lib/auth.ts:27) и [`authorizeCron`](src/lib/api-auth.ts:326).
Оба отклоняют **заглушки из репозитория** в production — то, что лежит в открытом
`.env.example`, знает любой, кто видел исходники.

| Переменная | Заглушка из `.env.example` | Поведение в production |
|---|---|---|
| `JWT_SECRET` | `replace_me_with_a_random_secret_of_at_least_32_characters` | приложение **не стартует**: `JWT_SECRET не задан или равен значению по умолчанию. Задайте свой случайный секрет …` |
| `CRON_SECRET` | `replace_me_with_another_random_secret_32_characters_ok` | cron-роуты отвечают **503** «CRON_SECRET равен значению-заглушке из .env.example. Задайте свой случайный секрет и перезапустите приложение.» |

Проверка вручную:

```powershell
# 1. JWT: положите заглушку в .env и попробуйте поднять контейнер
docker compose restart app
docker compose logs --tail 50 app
# Ожидание: панель не поднялась, в логах — сообщение о значении по умолчанию.

# 2. CRON: заглушка в CRON_SECRET, приложение уже запущено
curl -i "http://localhost:3000/api/daily-snapshot?key=replace_me_with_another_random_secret_32_characters_ok"
# Ожидание: HTTP/1.1 503 + текст про заглушку (а НЕ 403):
# это ошибка настройки сервера, а не «неверный ключ».
```

Дополнительно проверьте остальные ветки:

| Ситуация | Ожидание |
|---|---|
| `CRON_SECRET` пустой или из пробелов | **503** «CRON_SECRET не задан на сервере» — в любом режиме, не только в production |
| корректный `CRON_SECRET`, верный ключ | `200`; сравнение — timing-safe (`timingSafeEqual`), утечки по времени нет |
| корректный `CRON_SECRET`, неверный ключ | отказ |
| `JWT_SECRET` короче 32 символов | приложение работает, но в консоли предупреждение `[auth] JWT_SECRET короче 32 символов — рекомендуется усилить его до 32+ символов.` |
| вне production (`NODE_ENV != production`) | заглушка **допустима**: локальный запуск и тесты не должны ломаться |

> ℹ️ В `docker-compose.yml` оба секрета объявлены как обязательные (`${CRON_SECRET:?Укажите …}`,
> `${JWT_SECRET:?Укажите …}`) — без них `docker compose up` падает ещё до старта контейнера. Это
> первая линия защиты, проверка в коде — вторая.

**Шаг 10.2 — локальный биндинг порта БД**

| Звено | Что проверяем |
|---|---|
| Файл | [`docker-compose.yml`](docker-compose.yml:12) → `db.ports: "127.0.0.1:5432:5432"` |
| Команда | `docker compose port db 5432` |
| Ожидание | `127.0.0.1:5432` — база **не** публикуется наружу, подключиться можно только с самого сервера (или из `app` по внутренней сети Docker) |
| Дополнительно | `netstat -ano | findstr :5432` — адрес прослушивания `127.0.0.1`, а **не** `0.0.0.0` |

Если нужен доступ с рабочей машины — SSH-туннель, а не смена биндинга:

```powershell
ssh -L 5432:127.0.0.1:5432 user@сервер
```

> ⚠️ **Обратите внимание на комментарий в compose:** публикация `5432:5432` без префикса
> открыла бы базу в интернет. Проверяйте это после каждого обновления файла: замена `127.0.0.1`
> на `0.0.0.0` (или удаление префикса) — критичная регрессия, которую на стенде видно сразу.

**Шаг 10.3 — healthcheck контейнера `app`**

Healthcheck — это `curl -fsS http://127.0.0.1:3000/api/health || exit 1` каждые 30 секунд
(`interval: 30s`, `timeout: 5s`, `retries: 3`, `start_period: 15s`). В образ добавлен пакет
`curl`: в `node:alpine` его нет, и без него контейнер **навсегда** оставался бы `unhealthy`.

| Звено | Команда | Ожидание |
|---|---|---|
| Статус | `docker compose ps` | у `app` в столбце `STATUS` — **`(healthy)`**; у `db` — тоже `healthy`; у `migrate` — `Exited (0)` |
| Логи healthcheck | `docker inspect --format "{{json .State.Health}}" app` | `"Status":"healthy"`, в `Log` — успешные записи об `/api/health` |
| Сам пробник | `curl -fsS http://localhost:3000/api/health` | `{"ok":true}` |
| С диагностикой | тот же адрес с cookie администратора | `{"ok":true,"database":"reachable","uptimeSec":…,"nodeEnv":"production","checkedAt":"…"}` |

Проверьте и отрицательный случай: **остановите БД** при работающем `app`:

```powershell
docker compose stop db
docker compose ps
# Ожидание: app переходит в (unhealthy) — /api/health отдаёт 500, потому что БД недоступна.
curl -i http://localhost:3000/api/health      # 500, тело {"ok":false}
docker compose start db
```

> ⚠️ **Политика `restart: always` реагирует на выход процесса, а не на `unhealthy`.** Docker сам
> контейнер по этой проверке **не перезапустит** — статус нужен для `docker compose ps`, внешнего
> мониторинга и uptime-роботов. Не ждите автоматического восстановления.

**Шаг 10.4 — индексы в БД после миграции**

Схема применяется сервисом `migrate` (`drizzle-kit push --force` в

**Негативная проверка (что будет, если миграция не применилась):**

| Симптом | Что означает |
|---|---|
| в выводе запроса нет `division_members_roles_alert_idx` | задача контроля ролей всё равно работает, но `WHERE status = 'dismissed' AND roles_alert_sent_at IS NULL AND dismissed_at < …` идёт последовательным сканом: на большом составе цикл раз в 30 минут станет заметно дороже |
| применить миграцию вручную | `psql "$DATABASE_URL" -f scripts/migrations/2026-09-dismissed-roles-monitor.sql` — файл идемпотентен (`CREATE INDEX IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`) |

```sql
SELECT count(*) AS dismissed_without_date

 WHERE status = 'dismissed' AND dismissed_at IS NULL;
-- Ожидание: 0
```

# ЧАСТЬ 3. ЛОГИ, РАЗБОР И ОТКАТ

## 3.1. Где смотреть: три разных «лога»

Важно не путать: у системы **три** независимых места, где видно, что происходило.

| Место | Что там | Доступ |
|---|---|---|
| **Консоль приложения** (стандартный вывод) | технические сообщения бота и планировщика: принятые заявки, сверка ролей, контроль ролей исключённых, ошибки Discord API | оператор сервера |
| **`bot_logs`** — вкладка **Журнал** в панели | аудит-трейл: заявки, рапорты, решения, синхронизации, сверка ролей, контроль ролей исключённых, удаление профилей | командиры и администраторы |
| **`processed_requests`** | защита от повторной обработки заявки | SQL, в интерфейсе не показывается |

### 3.1.1. Консоль (Docker)

```powershell
docker compose ps                        # что вообще запущено
docker compose logs -f app               # живой поток (Ctrl+C для выхода)
docker compose logs --tail 200 app       # последние 200 строк
docker compose logs --tail 500 app | Select-String "\[bot\]"
docker compose logs --tail 500 app | Select-String "\[scheduler\]|\[maintenance\]|\[role-sync\]"
docker compose logs --tail 500 app | Select-String "\[roles-monitor\]"
docker compose logs --tail 500 app | Select-String "\[admin/members\]"
docker compose logs --tail 500 app | Select-String "\[init\]"
```

На что смотреть:

| Строка в консоли | Что означает |
|---|---|
| `[init] Инстанс …: роль=leader, запускаю фоновые задачи` | этот процесс ведёт бота и планировщик |
| `[init] Инстанс …: фоновые задачи уже ведёт другой инстанс` | **второй** процесс работает только как веб-сервер: если бот «молчит», проверьте, кто лидер |
| `[bot] Принята заявка: …` | разобрана заявка из канала ШДС или отпусков |
| `[bot] Роли обновлены: получатель …` | выполнен запрос ролей |
| `[bot] Не удалось снять роль «Отпуск»` | у роли бота нет права «Управление ролями» или она ниже в иерархии |
| `[scheduler] operation ping @ …: ok` | сработал пинг на операцию |
| `[maintenance] Фоновое обслуживание запущено: …` | синхронизация ШДС и копии работают |
| `[role-sync] сбой запуска сверки: …` | сверка не запустилась: обычно нет `guild_id` или бот на нескольких серверах |
| `[roles-monitor] Напоминание отправлено: <позывной> (<id>), ролей клана осталось N` | сценарий 8: комсоставу ушёл пинг о неснятых ролях |
| `[roles-monitor] <id>: роли подразделения уже сняты` | сценарий 8: боец проверен, повода для пинга нет |
| `[roles-monitor] <id>: участник не найден на сервере — роли неактуальны` | сценарий 8: 404 от Discord, роли ушли вместе с участником |
| `[roles-monitor] Ошибка проверки <id>: …` | сценарий 8: сбой запроса; боец останется кандидатом на следующий цикл |
| `[scheduler] roles-monitor: …` | итог цикла контроля ролей, печатается только когда были напоминания или ошибки |
| `[admin/members] Не удалось удалить профиль бойца: …` | сценарий 9: ошибка транзакции удаления (текст ошибки — только в логах сервера) |
| `[admin/members] Удаление прошло, но запись в журнал не удалась: …` | сценарий 9: профиль удалён, но аудит не записался; клиент получает успех |

Имена бойцов в консоли **специально обезличены** (`logRef` печатает короткий хеш) — это защита
персональных данных в логах контейнера. Узнаваемые данные ищите в панели, в журнале.

### 3.1.2. Журнал в панели (`/logs`)

Две вкладки:

- **«Сайт» (системные)** — с подфильтрами: `Все`, `Операции`, `Онлайн`, `Синхронизация`;
- **«Редактирование»** — всё, что меняет данные: заявки, рапорты, решения, роли, сверка.

Фильтр по категории отдаётся запросом `GET /api/logs?category=edit` (доступ — командир и выше).

Как читать запись: нажмите на строку — раскроются детали (`details`) со структурированными полями
(«Итог», «Изменения», «Выдано ролей», «Снято ролей» и т. п.).

Прямые запросы к журналу — когда нужно точное время и полный текст ошибки:

```sql
-- Последние 20 записей любого вида
SELECT id, created_at, category, kind, ok, title, detail FROM bot_logs ORDER BY id DESC LIMIT 20;

-- Только неуспешные операции за прогон
SELECT created_at, title, detail, error FROM bot_logs WHERE ok = false ORDER BY id DESC LIMIT 20;

-- Сверка и запросы ролей
SELECT created_at, title, details FROM bot_logs WHERE kind = 'roles' ORDER BY id DESC LIMIT 10;

-- Контроль ролей исключённых (сценарий 8): напоминания и сбои
SELECT created_at, title, detail, ok, error
  FROM bot_logs WHERE kind = 'roles-monitor' ORDER BY id DESC LIMIT 20;

-- Удаления профилей (сценарий 9): кто, кого и когда
SELECT created_at, author, action, details
  FROM bot_logs WHERE title = 'Удаление профиля бойца' ORDER BY id DESC LIMIT 10;
```

## 3.2. Типовые сбои и что делать

| Симптом | Причина | Что делать |
|---|---|---|
| Бот не реагирует ни на что | не заданы `moderator_role_id`, `command_role_id` или `leave_role_id` — `loadBotConfig()` бросает ошибку | в консоли строка `Не заданы обязательные настройки бота: …`; заполнить настройки |
| «роль не выдана», `guild_id не задан` | в `bot_settings` пусто `guild_id`, а бот состоит не на одном сервере | задать `guild_id` (см. 1.5.2) |
| `Missing Permissions` при выдаче роли | роль бота ниже управляемой в иерархии либо нет права «Управление ролями» | поднять роль бота выше всех (см. 1.3) |
| Сверка «работает», но роли не меняются | включён режим проверки (`role_sync_dry_run = true`) | так и задумано; снять тумблер «Роли не менять» |
| «Столбцы экзаменов не найдены в строке 6» | переименован заголовок норматива в шапке листа | вернуть исходный заголовок; см. `EXAM_TITLE_ALIASES` в `src/lib/gsheets.ts` |
| «Боец … не найден на листе» | позывной в панели не совпадает со строкой в таблице | сверить написание в панели и на листе |
| «Лист "…" не найден в таблице» | значение `unit` не равно имени листа | подразделение должно называться «Танковая рота» или «Артиллерийский дивизион» |

| Публикация рапорта/заявки не появилась в Discord | ошибка Discord не отменяет запись: в консоли `не опубликован` | решить заявку в панели `/admin/reports` — она уже в БД |
| Пинг на операцию не ушёл | пусто `discord_channel_id` | заполнить; в журнале будет «Пинг на операцию не отправлен» |
| Пинг уходит не в тот канал контроля вышедших | пусто `left_check_channel_id` | задать; иначе берётся канал пингов |
| Панель отдаёт 502 / недоступна | контейнер `app` не поднялся либо слушает только 127.0.0.1 | `docker compose logs --tail 200 app`, `docker compose ps` |
| «Слишком много рапортов подряд» | сработал лимит подачи: 15 рапортов за 10 минут на бойца | подождать или тестировать другим аккаунтом |
| Запрос из скрипта отклонён (403) | сработала CSRF-проверка: запрос помечен как межсайтовый | обращаться с того же домена либо через интерфейс панели |
| Реакция на заявку «не срабатывает» повторно | заявка уже в `processed_requests` | удалить строку из `processed_requests` (см. 3.3.2) |
| Контроль ролей исключённых ничего не делает | тумблер `roles_monitor_enabled` выключен | Настройки → «Контроль ролей исключённых» → «вкл»; в журнале при выключенной задаче — «Проверка выключена» |

| Напоминание приходит сразу после исключения | `roles_monitor_delay_hours` пуст или мусорный | `resolveAlertDelayMs` вернёт 24 ч, но проверьте значение: пустое/отрицательное трактуется как «по умолчанию» лишь при нечитаемом вводе |
| Пинг пришёл на бойца, у которого роли уже сняты | у бойца осталась роль АТК — пингуется именно она | сверить роли участника в Discord; проверьте, что роль комсостава задана (`command_role_id`) |

## 3.3. Откат: как убрать следы теста

### 3.3.1. Полный откат из резервной копии (самый надёжный)

```powershell
# 1. Остановить приложение, чтобы никто не писал в базу
docker compose stop app

# 2. Восстановить дамп, снятый в разделе 1.6
docker compose exec -T db psql -U postgres -d app_db < backup-before-staging.sql

# 3. Поднять обратно
docker compose start app
```

Перед восстановлением убедитесь, что `backup-before-staging.sql` не пустой. Копии, снятые кнопкой,
лежат в томе `backups` (каталог `/app/backups`, срок хранения — 7 дней, настраивается
`BACKUP_RETENTION_DAYS`). Их список виден в карточке «Резервное копирование», а каталог и размер —
в блоке «Состояние и занятое место».

### 3.3.2. Точечная чистка тестовых данных

```sql
-- 1. Удалить тестовые заявки на вступление и рапорты
DELETE FROM recruit_applications WHERE id IN (1,2,3);
DELETE FROM service_reports      WHERE id IN (10,11,12);

-- 2. Вернуть бойца в исходное состояние
UPDATE division_members
SET status = 'active', active = true, vacation = false,
    vacation_until = NULL, vacation_notified = false,
    warnings = 0, left_notified = false,
    -- поля контроля ролей исключённых (сценарий 8):
    dismissed_at = NULL, roles_alert_sent_at = NULL
WHERE id = 1;

-- 3. Снять «память» о тестовых заявках, чтобы их можно было обработать повторно
DELETE FROM processed_requests WHERE message_id IN ('ID_СООБЩЕНИЯ_1','ID_СООБЩЕНИЯ_2');

-- 4. Убрать записи журнала прогона (если они не нужны как доказательство)
DELETE FROM bot_logs WHERE id IN (…);

-- 5. Удалить тестовые сессии бойцов
DELETE FROM member_sessions WHERE member_id = 1;

-- 6. После сценария 9 (удаление профиля) откат невозможен:
--    строки бойца уже нет. Единственный путь — резервная копия
--    (см. 3.3.1) либо создание бойца заново через /admin/recruits.
```

Отдельно после сценария 8 (контроль ролей) снимите «память» о напоминаниях, иначе боец больше
не будет проверяться:

```sql
UPDATE division_members SET roles_alert_sent_at = NULL WHERE id = <id>;
DELETE FROM bot_logs WHERE kind = 'roles-monitor' AND id IN (…);
```

> ⚠️ **Пункт 3 — ключевой.** Пока строка в `processed_requests` есть, повторная реакция на ту же
> заявку считается уже обработанной, и бот молча ничего не сделает. Если кажется, что «бот не
> повторяет действие» — дело почти всегда в этом, а не в боте.

### 3.3.3. Откат Google Таблицы

Таблица не восстанавливается из дампа Postgres, поэтому работайте **в копии**. Варианты:

1. **Файл → История изменений** («Версии»): выбрать версию до прогона и восстановить.
2. Вручную: вернуть `Вакант` в изменённые ячейки, очистить закраску экзаменов
   (ПКМ → «Очистить» → «Формат»), удалить добавленные строки и строки с листа «Запас».
3. Радикально: скопировать исходный шаблон заново и подменить `gsheet_spreadsheet_id`.

### 3.3.4. Откат ролей Discord

Роли возвращаются вручную на тестовом сервере. Учтите поведение при удалении бойца из ШДС
(`SHDS_ACTIONS.REMOVE`): бот снимает **все** роли, кроме `@everyone`, и выдаёт «Друг АТК».
Поэтому состояние ролей полезно зафиксировать **до** теста — иначе восстанавливать будет нечего.

Порядок первого включения на боевом сервере:

1. Запустить с `role_sync_enabled = false` — бот работает, роли никого не меняет.
2. Нажать **«Проверить без изменений»**, разобрать отчёт. При расхождениях сначала исправить

3. Включить `role_sync_enabled = true` (сверка по расписанию), **оставив** «Роли не менять».
4. Снять «Роли не менять» — сверка переходит в боевой режим.
